# nagramxf-mirror

Обновления Nagram XF в виде нормальных GitHub-релизов.

Зеркало ничего не собирает само. APK собирает CI оригинального репозитория,
а я забираю его артефакт, проверяю подпись и публикую здесь одним файлом в
релизе. Байты приложения не трогаю и не переподписываю. Ахтунг, все скрипты писала нейронка.

## Как получать обновления на смартфон

Понадобится [Obtainium](https://obtainium.imranr.dev/):

1. **Add App** → `https://github.com/ashuuya/nagramxf-mirror`
2. **Include prereleases** — включить. Релизы помечаются как prerelease, чтобы
   они не смешивались со «стабильными» в отчётах и чужих инструментах.
3. Остальное можно оставить по умолчанию. Фильтр APK не обязателен (в релизе
   всегда один файл), страховка: `arm64-v8a\.apk$`
4. **Download only over Wi-Fi** — можно включить: каждая сборка тянет 100+ МБ.

Дальше всё само: Obtainium по своему интервалу видит новый релиз и предлагает
обновление. APK подписан тем же ключом, что и официальные релизы Nagram XF,
поэтому ставится поверх вашего текущего приложения без удаления и потери данных.

Хочется совсем тихую установку — ставьте
[Shizuku](https://shizuku.rikka.app/) (на Android 11+ активируется с телефона
через беспроводную отладку), выберите в Obtainium способ установки Shizuku и
включите фоновые обновления. Тогда имеет смысл выставить ещё и **Minimum age
for updates** (Obtainium ≥ 1.6.17) часа на 3–6: сборки девелоперские, и про
регессию в свежей обычно успевают написать в issues оригинала раньше, чем вы
её поставите.

Если сборка всё-таки оказалась больной — в карточке приложения в Obtainium
можно выбрать предыдущую версию.

## Почему это вообще существует

Последний релиз в оригинале — `12.10.1.1251` от 14.09.2026, а в ветке `dev`
уже давно `13.2.1`, и разрыв будет только расти. Тг-каналы встали
примерно тогда же: стабильный замолчал 14.09, бета — 05.10.

При этом сборки никуда не делись: CI оригинала продолжает собирать APK и
складывать их в артефакты GitHub Actions — ZIP примерно на 170 МБ с двумя
APK, который скачивается только залогиненным пользователем GitHub. Следить
за таким через Obtainium нельзя.

Вернуть публикацию релизов технически может и сам оригинал, но видимо не вернёт: джоба
автопубликации в его workflow закомментирована, а `permissions: contents: read`
не даёт CI создавать релизы в принципе. Поэтому это зеркало существует.

## Что происходит внутри

```
CI оригинала собирает 2 APK (arm64-v8a и armeabi-v7a) → ZIP ~170 МБ
                    ↓
   extract_from_remote_zip.py вытаскивает из него один arm64 APK (~86 МБ)
   точечными HTTP Range-запросами: EOCD → central directory → байты файла.
   Второй ABI и baseline-профили не скачиваются вообще.
                    ↓
   verify_signer.py сверяет сертификат подписанта с зашитым эталоном.
   Не совпал → ран падает красным, ничего не публикуется.
                    ↓
   сравнение SHA-256 с state.json: сборка не менялась → выходим без публикации
                    ↓
   gh release create → один .apk ассетом релиза
                    ↓
   prune: последние 20 релизов храним, остальное удаляем вместе с тегами
```

Ещё в notes каждого релиза попадает список коммитов апстрима, накопившихся с
предыдущей зеркальной сборки того же потока: воркфлоу спрашивает compare API
GitHub и перечисляет всё, что изменилось между сборками. Merge-коммиты из
списка спрятаны, а если коммитов больше тридцати, остаток отдаётся ссылкой.

Расписание — `13,43 * * * *` (каждые полчаса, UTC). Публичный репозиторий
получает безлимитные минуты Actions, так что денег это не стоит ни мне, ни
GitHub: холостой прогон заканчивается на шаге «изменилось ли?» и стоит один
API-запрос.

`keepalive.yml` дважды в месяц делает пустяковый коммит. Это обход правила
GitHub: в публичном репозитории scheduled-воркфлоу отключаются после 60 дней
без активности, причём собственные запуски воркфлоу активностью не считаются.
Правило странное, но спорить с ним дороже, чем кормить его коммитами.

## Подпись

Артефакты оригинала подписаны тем же ключом, что и его официальные релизы.
Я проверял это в лоб: сертификат подписанта ассета релиза `1251` побайтово
совпадает с сертификатом из `TMessagesProj/release.keystore`, лежащего в
открытом репозитории оригинала.

```
sha256 = 1a05a230b7d3c4703c79a5baf872396112669c4d716474be6f9e8247a54c4563
serial = 15055BB4
valid  = 2024-09-13 .. 2036-09-10
alias  = chen_hai
```

Отсюда два следствия. APK отсюда ставится поверх вашего Nagram XF без удаления:
совпадают и имя пакета (`fork.risin42.nagramx`), и ключ. И подменить содержимое
по дороге невозможно: воркфлоу сверяет сертификат до публикации, а не после.

Честная оговорка: я не могу проверить, что сам CI оригинала не собрал ничего
зловредного — здесь доверие к апстриму такое же, как у вас. Я гарантирую
другое: опубликовано ровно то, что собрал их CI, байт в байт.

Проверить любой файл вручную:

```bash
python3 tools/verify_signer.py NagramXF-v13.2.1-37a3538\(1252\)-plugin-arm64-v8a.apk
# OK: signed by the official NagramXF release key   (exit 0)
```

## Известные ограничения

- **Задержка.** «Свежая сборка» на практике означает «в пределах часа после
  готовности»: 14–30 мин собирает оригинал, до 30 мин ждём своего слота cron,
  ещё 15–60 мин может добавить планировщик GitHub, плюс интервал проверки
  Obtainium.
- **Не каждый коммит собирают.** В оригинале `paths-ignore` отсекает правки
  `**.md` и `.github/**`.
- **Две ветки — два потока.** `dev` → Staging build, `canary` → Canary build,
  одна и та же правка может попасть в обе с разным SHA и разницей в дни.
  Это зеркало подписано на `canary`; не подписывайтесь на оба.
- **Стабильность.** Это `canary`, а не релизы: регрессии случаются, примеры
  свежих — [#205](https://github.com/Keeperorowner/NagramXF/issues/205)
  и [#196](https://github.com/Keeperorowner/NagramXF/issues/196).
- **Play Protect** может ругаться на установку:
  [#105](https://github.com/Keeperorowner/NagramXF/issues/105).
- **nightly.link.** Воркфлоу качает артефакт через этот сервис: он проксирует
  публичные артефакты Actions без авторизации, при этом сам файл отдаётся с
  родного хранилища GitHub (`productionresultssa*.blob.core.windows.net`).
  Подмену исключает проверка подписи; если сервис умрёт, ран начнёт падать —
  это заметно сразу, а не тихо.
- **Если оригинал перестанет собирать**, nightly.link будет молча отдавать
  последнюю успешную сборку, и зеркало тоже будет молча её переиздавать…
  если бы не проверка возраста: ран пишет предупреждение в job summary,
  если сборке старше 14 дней. Смотрите на дату в релизе, если что.
